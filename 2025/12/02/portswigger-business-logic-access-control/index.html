Business Logic & Access Control — Patterns from 25 PortSwigger Labs

Created2025-12-02|Web Security

Scanners find injection. They almost never find logic bugs — price manipulation, workflow skips, broken object-level authorization — because those require understanding what the application is supposed to do. This post collects the recurring patterns I extracted after working through the access-control and business-logic tracks of the Web Security Academy.

Access control: the four shapes

Broken access control is rarely exotic. It’s almost always one of these:

1. Horizontal — IDOR / BOLA

An identifier in the path, query, or body references an object the server never checks you own:

The tell is a 200 returning someone else’s data. On UUIDs, don’t give up — look for the ID leaking elsewhere (a list endpoint, an email, a filename) and replay it into the detail endpoint.

2. Vertical — role escalation

A normal user reaching admin functionality:

  • Guessable admin path (/admin, /administrator-panel) gated only by a link the UI hides.
  • X-Custom-IP-Authorization: 127.0.0.1 or X-Forwarded-For: 127.0.0.1 trusted by the app.
  • A roleid / isAdmin field accepted in a profile-update body it shouldn’t parse (mass assignment).

3. Context-dependent

Access that depends on state — e.g. you can reach /admin only via a multi-step flow, so you skip the intended gate by requesting the final step directly.

4. Platform / referer-based

Access “enforced” by the Referer header or a front-end redirect — trivially forged or simply not followed.

Business logic: making the app do the impossible

Price and quantity manipulation

The classic: the client sends the price.

Or negative quantity to create credit, or an integer overflow on quantity to wrap the total. The lab where you add so many of a cheap item that the total overflows to a small positive number is the canonical example.

Coupon / discount logic

  • Alternating codes — the app dedupes consecutive identical codes, so SIGNUP30 → NEWCUST5 → SIGNUP30 → … stacks discounts to zero.
  • Gift-card loops — buy a $7 card that redeems for $10 store credit; repeat for infinite balance.

Workflow-order flaws

Multi-step flows that don’t re-validate earlier steps:

The server priced the order at step 2 and never rechecked at step 4.

The dual-use endpoint

A password-change form that also updates the username when you inject username=administrator and omit current-password — one endpoint doing two jobs with one authorization check.

The methodology that finds them

Logic bugs don’t come from payloads; they come from modeling the target first:

  1. Enumerate actors — anonymous, user, premium, merchant, admin, API client. What can each do?
  2. Map the state machine — register → verify → pay → fulfil; order → settle → ship; refund; withdraw. What changes at each step?
  3. Find the trust boundaries — client vs server, service vs service, tenant vs tenant, front-end validation vs back-end validation. Where do the two sides disagree?
  4. Ask “what assumption breaks here” for every step — can I skip it? replay it? send a value the UI never would?

For each candidate, the confirmation bar is strict: two-identity proof. With account A’s session you must retrieve or mutate account B’s private object — where B is provably another user, not public data. “The endpoint is reachable” or “the ID enumerates” is not a finding; reading another user’s record is.

Redline

On authorized targets, prove the class with the minimum action: one sibling object read, one coupon stacked once, one test object created and deleted. Never batch, never touch real users’ data, and log every write (object id, before → after, how to revert). A logic bug you can demonstrate on your own two test accounts beats a “possible” you couldn’t safely confirm.
