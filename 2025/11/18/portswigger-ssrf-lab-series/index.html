PortSwigger SSRF Lab Series — From Stock Check to Cloud Metadata

Created2025-11-18|Web Security

Server-Side Request Forgery (SSRF) is one of those bug classes that looks trivial in a lab and becomes devastating in production the moment a cloud metadata endpoint is reachable. This post walks through the PortSwigger Web Security Academy SSRF track end-to-end and distils the reusable methodology I apply on real targets.

The lab primitive

A 200 with a different Content-Length flags the live host. Then the same /admin/delete?username=carlos finishes it.

3. Whitelist / blacklist bypasses

Real apps rarely leave SSRF wide open. The interesting labs are the filters:

Filter Bypass
Blocks localhost / 127.0.0.1 http://127.1, http://[::1], http://2130706433/ (decimal), http://0177.0.0.1 (octal)
Blocks admin string Double URL-encode: %2561dmin; or mixed case AdMiN
Whitelists a domain, checks it appears in URL http://expected-host@evil-host/, http://evil-host#expected-host, or DNS names you control that embed the token
Whitelist by prefix http://whitelisted.com.evil.com/

The mental model: the filter and the HTTP client parse the URL differently. Every bypass lives in that gap — userinfo @, fragment #, alternate IP encodings, or a parser that stops at the first ..

4. Open-redirect chaining

When the URL is locked to a whitelisted origin, you don’t attack the fetch directly — you find an open redirect on the trusted origin and let it bounce you inward:

The whitelisted host issues a 302 to the internal target and the SSRF fetcher follows it. Two medium-looking bugs (whitelisted SSRF + open redirect) compose into a full internal-network read.

5. Blind SSRF via out-of-band

The most realistic case: no response reflection at all. Inject a Collaborator/interactsh payload into a header the server parses — classically the Referer:

A DNS+HTTP hit at your listener proves the backend reached out. Blind SSRF is still exploitable — internal port scanning by timing, or hitting an internal service with a known unauthenticated RCE.

Why this matters in production

On a live target the stock-check equivalent is any feature that fetches a URL you supply: webhook registration, image-proxy/avatar-by-URL, PDF/HTML renderers, URL import, link previews, SSO metadata fetch. The escalation ladder is always the same:

The single highest-value target is the cloud metadata service:

On AWS this returns a role name; one more hop returns temporary AccessKeyId / SecretAccessKey / Token. Redline for authorized testing: prove reachability (retrieve the role name, or a single whoami-equivalent metadata field) and stop — never enumerate or use the credentials against production.

Reusable checklist

  • Find every parameter that takes a URL, hostname, or path that the server dereferences.
  • Try localhost/127.1/[::1]/decimal-IP first — cheap, high signal.
  • If filtered, diff how the filter vs the HTTP client parse @, #, encoding, and prefix.
  • No reflection? Go out-of-band via Referer/Host/parsed headers.
  • Reachable? Walk the ladder to metadata, then stop at proof.

SSRF is a parser-confusion bug wearing a network-access costume. Solve it as a parser problem and the labs — and the real targets — fall the same way.
