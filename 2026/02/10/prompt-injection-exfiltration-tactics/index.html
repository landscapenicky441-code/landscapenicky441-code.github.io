Prompt Injection to Data Exfiltration — Practical Tactics for LLM Apps

Created2026-02-10|AI Agent Security

Prompt injection is talked about as a jailbreak trick. In application security it’s something more useful: a delivery mechanism for classic web bugs — data exfiltration, XSS, SSRF — that happen to route through a language model. This post is the tactical layer: what to inject, and how the data gets out.

Two paths into the model

Injection reaches the model two ways:

  • Direct — the attacker types into the chat (jailbreaks, tool-abuse instructions).
  • Indirect — the payload rides in on data the model later reads: a RAG document, a scraped web page, an email the agent summarises, a filename. This is the dangerous one, because the victim triggers it.

The high-value target is almost always indirect injection into an agent that acts on behalf of a logged-in user.

Exfiltration channels — getting the data out

An injected instruction is useless unless the model can leak what it read. The channels:

1. Markdown image rendering

If the app renders model output as Markdown, an injected image tag makes the client’s browser beacon out with data in the URL:

The image “loads” — a GET to the attacker with the exfiltrated data appended. No user click required.

2. Link unfurling

Chat platforms that auto-preview links will fetch an attacker URL server-side when the model emits it — same exfil, different trigger.

3. Markdown → HTML → XSS

If model output is rendered as HTML without sanitisation, injection becomes stored/reflected XSS:

Now the LLM is just the injection vector; the bug is a plain DOM XSS in how the app renders responses — an app-developer finding.

Hiding the payload

Indirect injection works better when the human reviewing the source can’t see it:

Invisible Unicode tags

Unicode Tag characters (U+E0000–U+E007F) render as nothing but are read by the model as text. An instruction encoded in tag characters is invisible in a document yet fully legible to the LLM.

Emoji variation selectors

Payload bytes smuggled after an emoji via variation selectors — visually a single emoji, semantically a hidden string.

Context-window overflow

Pad the input until earlier context — including the system prompt and its guardrails — falls out of the window, then issue the instruction into a model that has effectively forgotten its rules.

The four-step methodology

  1. Map the data flows — what does the model read (RAG, web, email, files) and where does its output render (Markdown? HTML? a tool call?)?
  2. Pick a channel — match an exfil path to how output is rendered (image beacon for Markdown, XSS for unsanitised HTML).
  3. Craft + hide — write the instruction, encode it to survive the source and evade human review.
  4. Confirm impact, attribute correctly — prove one benign token exfiltrates to your listener; decide whether it’s the provider’s, the app’s, or the user’s bug before reporting.

Attribution, again

The single most common way an AI report gets rejected is bad attribution. A model refusing or being jailbroken into disallowed text is usually the provider’s issue. It becomes the app’s the moment the injection:

  • reads or exfiltrates another user’s data,
  • fires a tool that changes state,
  • or renders into XSS in the app’s own UI.

Evidence standard

LLM behaviour is non-deterministic, so a single lucky run isn’t proof. For a credible report:

  • Show the payload, the rendered output, and the out-of-band hit (the request that arrived at your listener with the data).
  • Reproduce it more than once.
  • Keep the exfiltrated sample to a single non-sensitive token — enough to prove the channel, nothing more.

Redline

Everything above is for your own lab apps or authorized in-scope targets. Prompt injection that moves real user data, fires real tools, or renders real XSS is a real vulnerability — treat the confirmation exactly like any web bug: minimal proof, redacted data, one out-of-band token, and stop.

The takeaway: stop thinking of prompt injection as “tricking the chatbot.” Think of it as an untrusted-input problem where the parser happens to be a language model and the sink is your rendering layer, your tools, or your other users.
