Ghost Bits — Java char→byte Truncation as a WAF Bypass Primitive

Created2026-03-08|Web Security

One of the most elegant bug classes presented recently (Black Hat Asia 2026) is the “Ghost Bits” / Cast Attack: a whole family of WAF bypasses, path traversals, SMTP injections and request-smuggling primitives that all stem from a single Java quirk — a char silently losing its high byte when written as a byte. It’s worth understanding because the same root cause maps directly to what you grep for in a code audit.

Root cause: two views of the same character

A Java char is a 16-bit UTF-16 code unit. Plenty of older APIs write a char out as a single byte by silently discarding the high 8 bits and keeping only the low 8:

The validation runs at the char layer (full Unicode) while execution happens at the byte layer (truncated ASCII). The check view and the execution view disagree — and every bypass lives in that gap.

Concretely: pick a Unicode character whose low byte is the ASCII you actually want. U+0100–U+01FF all truncate to 0x00–0xFF. Want a / (0x2F) that a filter won’t see? Send U+F12F, U+FF2F, etc. — the filter sees an exotic letter; the sink sees /.

Any user-controlled string reaching one of these, after a validation step that inspected the full-width chars, is a candidate.

What it unlocks

The published CVEs show the range of impact from this one primitive:

  • CVE-2025-41242 (Spring) — path traversal via truncated separators.
  • CVE-2024-36401 (GeoServer) — the same truncation feeding an evaluation sink.
  • CVE-2025-57733 (Jira SMTP) — smuggling CR/LF (0x0D/0x0A) past a header validator to inject SMTP commands.
  • CVE-2026-21933 (JDK HttpServer) — control characters surviving into HTTP parsing → request smuggling.

The pattern generalises: path traversal (smuggle / and .), CRLF / header injection (smuggle \r\n), file-upload filter bypass (smuggle a real extension byte past a name check), and request smuggling (smuggle control bytes into the framing layer).

The general lesson

Ghost Bits is a specific instance of the most productive bug-hunting question there is: does every layer that touches this input agree on what it is? Encoding-, casting-, and normalisation-boundaries are where “the validator and the executor see different strings,” and that is precisely where SSRF whitelist bypasses, unicode XSS, and this char→byte truncation all come from.

Defensive takeaway

For defenders and auditors:

  • Validate at the byte layer, not the char layer — or normalise to bytes before validating.
  • Reject any input containing characters outside the expected charset instead of silently truncating.
  • In review, treat every (byte), & 0xff, and writeBytes on user data as a taint sink and trace it back to its source.

This is a defensive-research writeup of published technique and public CVEs — reproduce it only against your own builds or in-scope authorized targets, and prove the primitive with a single benign marker (a traversal to a known-safe file, one injected header line) rather than a live exploit.
