Whitebox Code Audit — A Source-to-Sink Taint Methodology

Created2026-04-05|Code Audit

Blackbox testing tells you that something is broken; whitebox source review tells you why, and catches the bugs no request ever reaches. This post is the methodology I use for whitebox audits across Java / Python / Go / PHP / JS-TS — a disciplined source-to-sink taint model rather than grepping for scary function names.

The core model: source → propagation → sink

Every injection-class vulnerability is the same shape:

A bug exists when taint flows from a source to a sink without an adequate sanitiser in between. The whole job of an audit is establishing that flow — or proving it’s broken.

Sources — where untrusted data enters

Framework-specific, but always the request boundary:

Don’t forget the second-order sources: database rows, cache entries, message-queue payloads, and file contents that were themselves attacker-influenced earlier.

Sinks — where it becomes a vulnerability

Class Sink examples
SQLi Statement.execute(sql), MyBatis ${...}, string-concatenated JPQL
Command injection Runtime.exec, ProcessBuilder
SSRF URL.openConnection, HttpClient, RestTemplate
Path traversal new File(path), Files.readAllBytes, FileInputStream
SSTI template engines fed a user string as the template
Deserialization ObjectInputStream.readObject, unsafe Jackson polymorphic typing
XXE DocumentBuilderFactory / SAXParser with external entities enabled

Sanitisers — the reason most flows are safe

The audit is not “found a sink → report.” It’s “traced source → sink → is there a real sanitiser?“:

  • Parameterised queries (PreparedStatement with bound ?) — kills SQLi. MyBatis #{} is safe; ${} is not.
  • Canonicalise-then-validate for paths (getCanonicalPath().startsWith(baseDir)).
  • Allow-lists (not deny-lists) for SSRF hosts and file types.
  • Framework auto-escaping for output contexts.

The most common false positive in automated tools is calling a flow vulnerable when a sanitiser it didn’t model sits in the path. The most common miss is a sanitiser that looks right but is bypassable (a deny-list, a replace("../","") that doesn’t loop, a canonicalisation done after the check).

Verification gates

To keep signal high I run each candidate flow through gates, only promoting it when it survives all of them:

  • G0 — reachable? Is the source actually attacker-reachable (public route, no auth wall that the flow doesn’t already pass)?
  • G1 — flows? Does taint actually reach the sink, or does a branch/return cut it off?
  • G2 — unsanitised? Is there truly no effective sanitiser, or is the one present bypassable?
  • G3 — impactful? What does firing the sink actually get — RCE, file read, data exfil? Rank by that, not by sink scariness.

A finding that clears G0–G3 is real. One that stalls at G2 with a plausible sanitiser is a note, not a report.

Parameter priority

Not all inputs deserve equal attention. History (public disclosure archives, framework CVE patterns) tells you which parameter names and code shapes are repeatedly vulnerable — file/path/template/redirect/url parameters, admin/import/export endpoints, anything doing reflection or dynamic class loading. Start there; it’s where the yield is.

Why whitebox beats scanning here

  • It finds logic and auth bugs — a missing @PreAuthorize, an ownership check that reads the wrong id — that no payload reveals.
  • It sees the sanitiser, so it separates “reachable sink” from “exploitable sink” without guessing.
  • It scales across a whole codebase in one pass instead of one request at a time.

Scope note

Whitebox review is for your own code or code you’re authorized to audit (employer, client engagement, open-source you’re reviewing responsibly). Findings go to the owner with the source→sink trace and a concrete remediation — parameterise this query, allow-list this host, canonicalise before this check. The trace is the report; it tells the developer exactly where and why.
